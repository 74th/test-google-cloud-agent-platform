## Context

既存ランタイムは `POST /api/reasoning_engine` と `POST /api/stream_reasoning_engine` を公開し、HTTP ミドルウェアがすべての受信パスと状態を記録する。通常の4操作は Cloud 上で動作確認済みだが、長時間実行クエリジョブは監視期限内に終了せず、コンテナ受信ログも得られなかったため「判定不能」としている。前回の検証環境は `terraform destroy` 済みであり、Agent Platform エージェント、Artifact Registry、サービスアカウント、GCS バケットなどの検証用リソースは残っていない前提とする。

Google からは `POST /` を追加すると長時間実行クエリがそこへ配送されたとの情報がある。ただし、ルートパスへの到達だけでは、要求形式の解釈、エージェント処理、ジョブ完了、GCS 出力まで成功したとはいえない。動機と変更範囲は [proposal.md](proposal.md)、観測可能な振る舞いは delta spec を参照する。

## Goals / Non-Goals

**Goals:**

- 既存の単項ハンドラーをルートパスでも利用し、処理差による比較ノイズをなくす。
- HTTP 配送、要求解釈、処理完了、ジョブ最終状態、GCS 出力を別々の証跡として保存する。
- 以前の検証と比較できるコマンド、タイムアウト、ログ検索条件、結果形式を用いる。
- ライブ検証の結果が成功でも失敗でも、再実行可能な形で結論と根拠を残す。

**Non-Goals:**

- Agent Platform 側の内部配送実装や一般的な BYOC サポート範囲を証明すること。
- ルートパスで任意の未知ペイロードを無条件に成功扱いすること。
- 長時間処理を別サービスや独自キューで代替すること。
- 既存の通常クエリ操作やストリーミング契約を変更すること。

## Decisions

### 1. ルートパスを既存の単項ハンドラーへ割り当てる

同じ FastAPI ハンドラーに `POST /` と `POST /api/reasoning_engine` の2つのルートを割り当て、入力検証、許可操作、応答形式、処理ログを共有する。ルート専用の複製ハンドラーを作る案は、将来の修正差分によって検証結果が変わるため採用しない。

ルートパスへ未知の形式が届いた場合は既存の安全な 4xx と HTTP ライフサイクルログを残す。検証の第一段階では配送確認として扱うが、正常動作とは判定しない。受信内容を調べるために本文全体をログへ出す案は、入力や認証情報を漏らす可能性があるため採用しない。

### 2. ローカルテストで2つの単項パスの同値性を固定する

同じ有効入力を両方のパスへ送り、応答内容、状態コード、処理イベントが一致することを自動テストする。無効入力についてもルートパスが安全な 4xx を返すことと、本文中の秘密値がログへ出ないことを確認する。これにより、Cloud 検証前にルーティング追加そのものの回帰を切り分ける。

### 3. 長時間ジョブの証跡を一つの試行記録へ集約する

検証 CLI は試行 ID、対象エージェント、ジョブ名、開始・終了時刻、状態遷移、出力 URI、ログ検索範囲と検索結果を JSON Lines に記録する。ログは対象リソース、時間範囲、`POST /` の受信イベントを基準に収集し、検証マーカーを処理ログまたは出力で照合する。

マーカーだけを検索する既存方式では、入力検証前に拒否されたルート要求を見落とす。反対に、時間範囲内のルートアクセスだけでは別試行との混同が起こるため、検証中は対象エージェントに対する長時間ジョブを直列に実行し、リソース識別子、ジョブ時刻、リクエスト ID、検証マーカーを使える範囲で組み合わせる。

### 4. 成否を段階別に判定する

最終結果には `http_delivery`、`processing`、`job_terminal_state`、`gcs_output` の各段階を成功・失敗・判定不能として保持する。すべての成功証跡が揃った場合だけ全体を「動作確認」とし、HTTP 到達後に失敗した場合は「配送確認・動作未確認」、十分な条件で HTTP 到達がない場合は「未到達」、証跡が不足する場合は「判定不能」とする。

単一の真偽値にする案は、Google の情報で確認したい「ルートへ配送される」と、利用者が知りたい「長時間ジョブが完了する」を混同するため採用しない。

### 5. Terraform で検証基盤を再作成してから新しいイメージをデプロイする

前回の検証基盤は削除済みのため、クラウド検証は Terraform の設定値を確認し、`terraform init`、`terraform plan`、`terraform apply` で Artifact Registry、サービスアカウント、IAM、GCS バケットなどを再作成するところから開始する。apply の出力と作成対象を確認した後、新しいタグでコンテナを build・push し、新規の検証用エージェントをデプロイする。エージェントがその image URI を参照していることを記録してからジョブを実行し、デプロイ情報とライブ検証結果には image URI と実行日時を残す。

削除済みのリソースが存在する前提で build、push、エージェント作成を先に試す案は、Artifact Registry や実行サービスアカウントがなく途中で失敗するため採用しない。

## Risks / Trade-offs

- [実際のルート要求形式が既存の単項ランタイム要求と異なる] → HTTP 配送と 4xx を証跡として保存し、秘密値を記録せずにエラー種別と入力構造上の不足箇所を切り分ける。
- [Cloud Logging の取り込み遅延で未到達と誤判定する] → ジョブ終了または監視期限後に明示した猶予を設け、検索範囲と実行時刻を結果へ記録する。
- [ルートパスのヘルスチェック等をジョブ配送と誤認する] → POST メソッド、対象 revision、時刻、リクエスト ID、処理ログ、検証マーカーを段階的に照合し、関連付け不能なら判定不能とする。
- [ジョブが長時間 RUNNING のままになり費用が増える] → 有限の監視期限を設け、期限超過を最終成功とせず、利用可能な停止・削除手順を実施する。
- [ルートパス追加で攻撃面が増える] → 既存と同じ厳格な入力検証・許可操作・安全なログを共有し、汎用プロキシや本文ダンプにはしない。

## Migration Plan

1. ルートパスのローカル同値性・エラー・ログテストを追加し、既存テスト一式を通す。
2. 検証 CLI の段階別証跡収集と判定を実装し、クラウドアクセスを必要としない部分をテストする。
3. Terraform の環境固有値を設定し、`terraform init`、`terraform fmt -check`、`terraform validate`、`terraform plan` を実行して再作成対象を確認する。
4. `terraform apply` を実行し、Artifact Registry、サービスアカウント、IAM、GCS バケットなどの検証基盤と出力値を確認する。
5. 新しいイメージタグを build・push し、新規の検証専用エージェントへデプロイして image URI と revision を保存する。
6. 通常の単項・ストリーム操作をスモークテストし、既存契約に回帰がないことを確認する。
7. 長時間実行クエリジョブを直列に1試行実行し、状態、ログ、GCS 出力を猶予時間後まで収集する。
8. 段階別の判定と総合結論を README または機密情報を含まない結果文書へ記録する。
9. 検証用エージェントを削除し、`terraform destroy` で今回再作成した検証基盤を削除して残存リソースを確認する。

ロールバックは `POST /` のルート登録を除いた以前のイメージを検証用エージェントへ再デプロイすることで行う。保存済みの検証結果は比較証跡として残す。
