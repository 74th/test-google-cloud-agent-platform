## Context

現リポジトリは最小の Python プロジェクトであり、ランタイム、コンテナ、Google Cloud 構成、検証クライアントは未実装である。動機は [proposal.md](proposal.md) を参照する。

Agent Platform のカスタムコンテナ契約では、`0.0.0.0:8080` の待受け、単項用 `/api/reasoning_engine`、ストリーム用 `/api/stream_reasoning_engine`、およびデプロイ時の `classMethods` 宣言が必要になる。API モード `""` と `"async"` は単項エンドポイントへ、`"stream"` と `"async_stream"` はストリームエンドポイントへルーティングされる。公式の長時間実行クエリジョブは最大7日間の処理を想定している一方、説明は ADK エージェントを参照しており、BYOC の任意クラスメソッドへどのように配送されるかは明示されていない。このため長時間ジョブは成功を前提にせず、到達有無を証跡から判定する探索的検証とする。

参照 PoC `/home/nnyn/ghq/github.com/74th/test-google-cloud-agent-platform/20260801-agent-hosting` から、ローカル Docker build/push、`agentplatform.Client` によるカスタムエージェント作成、専用サービスアカウント、Artifact Registry 読み取り権限の構成を再利用可能な知見として扱う。ただし、この PoC 固有の Claude SDK、モデル、時刻表ロジックは持ち込まない。

## Goals / Non-Goals

**Goals:**

- 4つのクラスメソッドを同じ薄いダミーエージェントで実装し、同期・非同期というクライアント契約と単項・ストリームという配送形態の差を切り分ける。
- ローカルテストと Cloud 上のライブ検証で同じ期待値を使い、応答内容、順序、時刻、ログを照合可能にする。
- 長時間ジョブについて、成功・失敗だけでなくコンテナ到達の有無を再現可能な証跡として残す。
- 検証用リソースを最小権限で作成し、明示的に削除できるようにする。

**Non-Goals:**

- 実用的な生成 AI、会話状態、ADK セッション、ツール呼び出しを実装すること。
- Agent Platform 自体の時間精度や配送保証を証明すること。
- 長時間ジョブが BYOC で未サポートだった場合に、プラットフォームを迂回して擬似実装すること。
- CI から実 Google Cloud リソースを自動作成すること。

## Decisions

### 1. FastAPI の2エンドポイントから4メソッドへディスパッチする

`DummyAgent` は `query`、`async_query`、`stream_query`、`async_stream_query` を公開し、HTTP 層は `class_method` を許可リストで解決する。単項エンドポイントは前2つだけ、ストリームエンドポイントは後2つだけを許可する。デプロイ構成でもそれぞれ `""`、`"async"`、`"stream"`、`"async_stream"` と宣言する。

この構成は公式ランタイム契約のルーティングをそのまま観測でき、メソッドごとにエンドポイントを増やすより Agent Platform 内部の配送条件に近い。単一の汎用ハンドラですべてを無条件実行する案は、誤った API モードでも成功してしまうため採用しない。

### 2. 待機には非ブロッキングな単調時計を使う

全メソッドの内部待機には `asyncio.sleep` を用い、計測には壁時計ではなく単調時計を使う。単項操作は開始から10秒まで待機する。ストリーム操作は開始から5秒で第1チャンクを生成し、さらに5秒待って第2チャンクを生成する。許容差はユニットテストでは注入可能な待機関数により決定的に検証し、実時間を使う結合テストでは環境差を見込んだ範囲を設ける。

同期メソッドを `time.sleep` で実装する案は FastAPI ワーカーをブロックして非同期操作との比較を歪めるため採用しない。ここでの「同期」は Agent Platform の `api_mode` とクライアントの利用形態を指し、サーバー内部のイベントループを塞ぐことは要件ではない。

### 3. ストリームは1行1オブジェクトの NDJSON とする

各チャンクを `{"output": "..."}` として JSON 化し、改行で区切る。レスポンス生成はバッファリングせず、最初のチャンクを生成した時点で送信できる `StreamingResponse` とする。これは公式の `/api/stream_reasoning_engine` 例と一致し、クライアントが順序と到着時間を独立して記録できる。

SSE をコンテナから直接返す案は、Agent Platform の外側の REST API が `alt=sse` を提供することと、コンテナ内部契約の NDJSON を混同するため採用しない。

### 4. 構造化ログと検証マーカーで処理を相関する

標準出力へ1行 JSON で `timestamp`、`severity`、`event`、`request_id`、`class_method`、`elapsed_ms`、`status` を出力する。HTTP ミドルウェアが全リクエストの受信と完了を、ディスパッチャがエージェント処理の開始、チャンク生成、終了、失敗を記録する。クライアントが入力に一意な `verification_id` を付け、ランタイムは値の長さと文字種を検証したうえでログ項目として記録する。任意の入力本文、Authorization ヘッダー、トークンは記録しない。

Cloud Logging の文字列検索だけに依存する案より、同一試行の API 応答とコンテナログを明確に照合できる。プラットフォームが入力をコンテナへ配送しない長時間ジョブではマーカーが存在しないこと自体を「未到達」の証跡として扱う。

### 5. ローカル検証とライブ検証を分離する

pytest はエージェントロジック、HTTP 契約、ログ、エラー、応答順序をローカルで自動検証する。CLI は `local` と `deployed` の対象を持ち、4操作を個別または一括実行し、各イベントを JSON Lines 形式で出力する。デプロイ済み検証は Agent Platform SDK の動的メソッドを基本経路とし、問題の切り分け用に REST 呼び出しも用意する。

実 Google Cloud 検証を通常の pytest に含める案は、認証、費用、所要時間、環境依存性が高いため採用しない。ライブ検証は明示的なコマンドとチェックリストで実施する。

### 6. Google Cloud 構成は参照 PoC を最小化して踏襲する

Terraform で必要 API、専用 Artifact Registry、専用ランタイムサービスアカウント、必要な IAM を管理する。イメージはローカル Docker で build して Artifact Registry へ push し、作成スクリプトで4つの `classMethods` を宣言する。環境固有値は環境変数または git 管理外の tfvars から与える。

既存 PoC のリソースを暗黙に共有する案は、検証結果と削除対象が混ざるため採用しない。既存コードはコピー元ではなく比較対象として使い、この PoC 固有の表示名とリポジトリ名を付ける。

### 7. 長時間ジョブは独立した観測ワークフローにする

ライブ検証 CLI は一意な検証マーカーを含むクエリと GCS 出力先を指定して `run_query_job` を開始し、返却されたジョブ名、開始時刻、入力、出力 URI をローカルの結果ファイルへ保存する。その後 `check_query_job` を一定間隔でポーリングし、終了または設定した監視期限まで状態遷移を追記する。併せて対象エージェントの Cloud Logging を開始前後の時刻と検証マーカーで検索し、GCS 出力の有無・内容を確認する。

判定は「コンテナ受信ログあり」を到達確認、「ジョブ開始済みかつ十分な監視期間とログ検索を満たすが受信ログなし」を未到達、権限・ログ・期限などの証跡不足を判定不能とする。無限ポーリングは行わず、期限超過時点の状態を保存する。REST `:asyncQuery` の GCS 入力方式は SDK の直接 query 方式と意味が異なるため、基本検証後の追加切り分け経路として文書化する。

## Risks / Trade-offs

- [Agent Platform のプレビュー仕様や SDK が変更され、メソッド名・作成 API が変わる] → 依存バージョンを固定し、公式ドキュメント確認日と operation schema を検証結果へ保存する。
- [中間プロキシやクライアントのバッファリングで5秒時点のチャンクが遅延する] → コンテナ直アクセスのローカル結果と Cloud 経由の結果を分けて記録し、チャンク内容と順序を必須、時刻は許容範囲付きで評価する。
- [10秒の処理がプラットフォーム側タイムアウトやコールドスタートの影響を受ける] → クライアント経過時間とコンテナ内部経過時間を別々に記録し、原因を切り分ける。
- [長時間ジョブはカスタム BYOC のクラスメソッドへ配送されない可能性がある] → 未到達を失敗で隠さず、ジョブ状態、GCS、ログ検索範囲を含む有効な結果として残す。
- [Cloud Logging の取り込み遅延で未到達と誤判定する] → ジョブ終了後にも猶予時間を設けて再検索し、猶予を満たせない場合は判定不能にする。
- [Google Cloud リソースに費用が残る] → リソース名を出力・保存し、検証手順の最後にエージェント削除と Terraform destroy の確認を置く。

## Migration Plan

1. ローカルで依存関係を同期し、ユニットテストと HTTP 結合テストを実行する。
2. コンテナを build・起動し、4操作のローカル実時間スモークテストとログ照合を行う。
3. Terraform の plan を確認して検証専用リソースを作成する。
4. コンテナを Artifact Registry へ push し、4メソッドを宣言したエージェントをデプロイする。
5. operation schema を保存し、4操作のライブ検証と Cloud Logging の照合を行う。
6. GCS 出力先を準備し、長時間実行ジョブを開始・監視・判定する。
7. 結果ファイルを機密情報なしで整理し、エージェントを削除する。不要なら Terraform 管理リソースも削除する。

ロールバックは新規作成したエージェントリソースの削除と、必要に応じた Terraform destroy で行う。本変更は既存サービスやデータの移行を伴わない。
