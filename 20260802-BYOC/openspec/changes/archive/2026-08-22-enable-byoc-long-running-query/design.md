## Context

長時間ジョブ用 SDK はクエリ文字列を GCS オブジェクトへ保存し、内部で REST `:asyncQuery` に実入力・実出力 URI を渡す。Agent Platform は専用の `job-container` と `proxy-container` を起動し、proxy が実行サービスアカウントとして入力を取得してから `http://localhost:8080/` へ配送する。

現状の実行サービスアカウントにはバケットの `roles/storage.objectAdmin` があるが、プロジェクトの `serviceusage.services.use` がなく、proxy は HTTP 配送前に403で失敗する。既存の証跡収集はアプリ固有イベントだけを対象にしているため、この proxy エラーとコンテナ再試行を結果へ含められなかった。また、現在の `/` は通常操作と同じ厳密な `class_method` を要求する一方、SDKが保存する長時間ジョブ入力にはそのフィールドがない。

## Goals / Non-Goals

**Goals:**

- GCS 取得、ルート配送、アプリ処理、出力保存の各境界で成功・失敗を特定する。
- 通常4操作の契約を維持したまま、長時間ジョブ用 `POST /` の入力を明示的に扱う。
- 約10秒の疎通試験と15分超の耐久試験を同じ証跡形式で実行する。
- IAM とログ収集を再現可能な構成として管理する。

**Non-Goals:**

- Google側が未保証としている最大実行時間を保証すること。
- 検証用 DummyAgent を本番エージェント実装へ置き換えること。
- 入出力本文、アクセストークン、署名付きURLなどの機密情報を結果へ保存すること。

## Decisions

### 1. 実行サービスアカウントへ Service Usage Consumer を付与する

Terraform で実行サービスアカウントにプロジェクトレベルの `roles/serviceusage.serviceUsageConsumer` を付与する。既存のバケットレベル `roles/storage.objectAdmin` は入出力オブジェクトの読み書きに使用し、役割を分けて維持する。

GCS権限だけを増やす案は、観測済みの拒否対象が `serviceusage.services.use` であるため採用しない。広い Editor 権限を付ける案も最小権限を満たさないため採用しない。

### 2. `/` を長時間ジョブ用の明示的な正規化境界にする

`/api/reasoning_engine` は既存の操作名必須契約を維持する。`/` は GCS に保存された `{"input": {...}}` 形式を受け付け、操作名がない場合だけ `query` として正規化する。操作名が明示される場合は非ストリーミングの許可操作だけを受け付ける。

すべてのエンドポイントで入力モデルを緩める案は、通常操作の誤入力検知を弱めるため採用しない。GCS入力に常に `class_method` を追加するだけの案は最小変更だが、Google側の成功例のようなアプリ固有入力を `/` が直接扱う契約との互換性が低いため、ルート側でも正規化する。

### 3. 検証用処理時間は入力で明示し上限を設ける

長時間ジョブ入力に任意の `delay_seconds` を追加し、未指定時は10秒、15分超試験では960秒を使用する。値は正の整数かつ検証用上限以下に制限し、待機には非ブロッキングな仕組みを使う。通常操作の operation schema と既定時間は変更しない。

環境変数でイメージごとに時間を変える案より、一つの検証イメージで短時間試験を成功させてから同じリビジョンを長時間試験でき、差分を減らせる。

### 4. SDK応答の実 URI を証跡の基準にする

SDKは指定された出力ファイル名から `_input` 名を生成し、ディレクトリ指定時には入出力名を生成する。そのため、CLI引数ではなく `run_query_job` 応答の `input_gcs_uri` と `output_gcs_uri` を保存し、存在確認にも実出力 URI を使う。REST直呼びは同一入力での比較経路として残すが、SDKと別機能とは扱わない。

### 5. proxy と job のログを段階別に収集する

ReasoningEngine リソースIDと時間範囲で検索したうえで、`labels.container_name` を保存する。`proxy-container` の GCS取得・HTTP配送エラー、`job-container` の起動・構造化ライフサイクルイベント、UvicornのHTTPステータスを別々に要約する。構造化イベントは `jsonPayload.event`、基盤エラーは `textPayload` と severity を対象にする。

保存するエラーはコンテナ名、段階、HTTP/gRPCコード、権限名、エラー種別に限定し、URLクエリや本文を除去する。operationが終端した場合はAPIの最終エラーコードと安全化したメッセージも保存する。

### 6. 短時間成功を長時間試験のゲートにする

まず10秒入力で、GCS取得、`POST /` の200、成功終端、実出力オブジェクトを確認する。いずれかが失敗した場合は15分超試験を開始しない。成功後、同じエージェントへ960秒入力を送り、監視期限を少なくとも処理時間プラス10分に設定して自動キャンセルせず終端を待つ。

## Risks / Trade-offs

- [Service Usage Consumer をプロジェクト単位で付与する] → 専用サービスアカウントだけを対象にし、検証環境の削除手順へ IAM の除去確認を含める。
- [proxy の実際の配送本文がSDKバージョンで変わる] → ルート正規化を限定的にし、4xxと安全なvalidation情報を証跡へ残す。
- [960秒試験がプラットフォーム側制限で失敗する] → 短時間経路成功を先に証明し、operation・proxy・jobのどの境界で失敗したかを報告する。
- [広いログ検索で機密情報を取得する] → 取得時点で許可フィールドへ要約し、原文を結果ファイルへ書き込まない。
- [SDKの表示状態とoperation終端状態が異なる] → 両方を同じジョブ名で記録し、operationのエラーを失敗理由の根拠に含める。

## Migration Plan

1. Terraform の IAM 変更を plan し、対象が専用実行サービスアカウントへの1ロール追加であることを確認して適用する。
2. ルート正規化、処理時間指定、証跡収集をローカルテストとコンテナテストで検証する。
3. 新しいイメージを検証専用エージェントへデプロイし、通常4操作の回帰試験を行う。
4. 約10秒の長時間ジョブ経路を実行し、全段階の成功を確認する。
5. 同じリビジョンで960秒のジョブを実行し、成功終端と出力を確認する。
6. 失敗時は直前のイメージへ戻し、IAM は原因調査に不要なら Terraform で除去する。
